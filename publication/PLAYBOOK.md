**В `y_stress.pkl`, на котором обучались все шесть моделей статьи, лежат не те
величины, которые заявлены.** По плоскостям это
`(S.Max. Prin, S.Mid. Prin, S.Min. Prin, σ_rr)` — три главных напряжения и

Следствия, которые нельзя обойти:

* физический лосс считал `∂σ₃/∂r + (σ₃ − σ₁)/r` — это не уравнение равновесия
  и вообще не тождество;

  которым код зануляет значение, действительно там нулевые. Проверка ГУ
  проходила, физика внутри области была не та. Именно поэтому дефект дожил до
  подачи;
* сравнение шести моделей как регрессионный бенчмарк на четырёх скалярных полях
  остаётся корректным — все обучались на одном и том же. Аннулируется физическая

### 0.1 Замечания рецензентов

Три содержательные дыры остаются в силе:

1. сравнение проведено на случайном hold-out из того же пространства
   параметров → показана интерполяция, а не обобщение (E-07);
2. каждая модель обучена **один раз**, без повторов по сидам → разница
   0.4–0.8 МПа между бэкендами статистически не установлена (E-08);
3. вывод «backend matters» опирается на описание протокола, которого нет в
   коде (E-05) — и, более того, **не имеет механизма**: «третий бэкенд»
   DeepXDE сконфигурирован как `DDE_BACKEND=pytorch`, то есть это тот же
   PyTorch за другим API. Производные torch и JAX на одних весах совпадают до
   8.7e-15 (E-19).

### 0.2 Дефекты, найденные при проверке кода и данных

4. **свободная поверхность стоит не там.** Окно «25–75 %» — осевое, а не
   радиальное; 20 точек профиля покрывают весь радиус, поэтому поверхность при
   `r_norm = 1`, а не 1.5. ГУ налагалось на радиусе `1.5 R`, вне материала, а
   измерялось при `r_norm = 1` (E-01);
5. **редукция уравнений равновесия оправдана только наполовину.** Для
   радиального уравнения отброшенный `∂τ_rz/∂z` даёт 1.3 % от удержанных
   членов — редукция законна. Для осевого отброшенный `∂σ_zz/∂z` даёт 68 % —
   выражение `∂τ_rz/∂r + τ_rz/r` осевым равновесием не является (E-02);

## 2. Предмет исследования

### 2.1 Процесс

Осесимметричное **холодное волочение проволоки** из низкоуглеродистой стали
**AISI 1020** через коническую волоку. После волочения остаются **остаточные
напряжения**, определяющие размерную стабильность, усталостную прочность и
надёжность. Прямой расчёт — МКЭ (Abaqus), дорогой для многократного
использования при проектировании; отсюда **суррогатные модели**,
предсказывающие профиль напряжений по параметрам процесса за миллисекунды.

### 2.2 Расчётная область и обозначения

Осесимметричная задача в координатах (r, z). Пять характерных поверхностей:
S₁ — ось симметрии, S₂ — выходная поверхность (задана скорость волочения),
S₃ — свободная боковая поверхность, S₄ — контакт с волокой, S₅ — вход
заготовки. Геометрия: α — полуугол рабочего конуса волоки, D₀ и D — диаметры
заготовки и готовой проволоки, L — длина калибрующего пояска.

### 2.3 Параметры (входы модели)

| Символ | Смысл | Уровни |
|---|---|---|
| Q | относительное обжатие по диаметру | 0.015, 0.025, 0.05, 0.10, 0.15, 0.20, 0.25 |
| k | коэффициент калибрующего участка | 0.0, 0.1, 0.3, 0.5, 0.75, 1.0 |
| α | полуугол волоки, град | 4, 8, 12, 16, 20 |
| μ | коэффициент трения Кулона | 0.025, 0.05, 0.10 (**три**, см. §5.3) |
| v | скорость волочения, м/мин | 5, 10, 20, 40, 250 |

`Q` — относительное уменьшение **диаметра**: при `D₀ = 36` мм и `Q = 0.10`
измеренный выходной радиус 16.2 мм = `18·(1 − 0.10)`. Проверено по координатам
узлов в `.rpt`.

Шестой вход — нормированная радиальная координата `r_norm`.

> **[изменено v2] Что означает `r_norm`.** Прежний handover утверждал, что
> `r_norm ∈ [0, 1]` соответствует 25–75 % сечения, а свободная поверхность
> лежит при `r_norm = 1.5` (`r_phys = R·(0.25 + 0.5·r_norm)`). Это неверно.
> Порог 25–75 % применяется к **осевой** координате `z` — берутся узлы из
> средних 50 % осевого размаха, зона выхода процесса на стационар. Внутри
> этого окна узлы сортируются по радиусу и сворачиваются в 20 бинов, поэтому
> профиль покрывает **весь** радиус:
>
> ```
> r_norm = 0  →  ось симметрии
> r_norm = 1  →  свободная поверхность (r_phys = R)
> ```
>
> Подтверждено на 2443 наборах: медиана `r_max(окно)/R = 0.996`, медиана доли
> осевого размаха в окне 0.4985, средний `|σ_rr|` в крайней точке 3.8 МПа
> против `|σ_θθ|` 114 и `|σ_zz|` 129 МПа (`audit/RAW_AUDIT.md`, §2–3).

### 2.4 Выходы

Четыре компоненты тензора остаточных напряжений в цилиндрических координатах,
по 20 радиальным точкам профиля:

```
(σ_rr, σ_θθ, σ_zz, τ_rz)   [МПа]
```

> **[изменено v2]** Это постановка. В `y_stress.pkl`, на котором обучались
> модели отклонённой версии, лежат другие величины — три главных напряжения и
> σ_rr (ERRATA E-18). Датасет пересобран из сырых `.rpt`
> (`publication/code/dataset.py`); все результаты новой версии относятся к
> пересобранным данным, и это надо написать в статье прямо.
>
> Масштабы компонент различаются на два порядка: `mean|σ_normal| ≈ 79` МПа
> против `mean|τ_rz| ≈ 0.67` МПа. Поэтому macro-RMSE, усреднённая по четырём
> компонентам, почти целиком определяется нормальными; рядом с ней надо
> печатать нормированную macro-NRMSE и покомпонентные значения, иначе про τ_rz
> в метрике не видно ничего.

### 2.5 Физика, которая закладывается в PINN

**Полная осесимметричная форма уравнений равновесия:**

```
∂σ_rr/∂r + ∂τ_rz/∂z + (σ_rr − σ_θθ)/r = 0        (1)
∂τ_rz/∂r + ∂σ_zz/∂z + τ_rz/r         = 0        (2)
```

**Что реально считается.** `z` не входит во вход сети, осевых производных нет:

```
R₁(r) = ∂σ_rr/∂r + (σ_rr − σ_θθ)/r
R₂(r) = ∂τ_rz/∂r + τ_rz/r
```

> **[изменено v2] Насколько это законно — численно.** Отброшенные члены
> оценены по сырым полям (`audit/RAW_AUDIT.md`, §6): поля внутри осевого окна
> биннингованы на сетку 20 × 20, производные — `numpy.gradient`, по каждому
> набору берётся медиана модуля члена.
>
> | уравнение | отброшено | отношение к сумме удержанных | сдвиг невязки |
> |---|---|---|---|
> | (1) радиальное | `∂τ_rz/∂z` | 0.013 | 6 % |
> | (2) осевое | `∂σ_zz/∂z` | 0.68 | 32 % |
>
> Для (1) редукция обоснована и это можно писать в статье. Для (2) — **нет**:
> отброшенный член того же порядка, что удержанные, и `R₂` осевым равновесием
> не является. Прежний handover предлагал «привести уравнения в статье к тому,
> что реально считается, и объяснить малость `∂/∂z`» — для второго уравнения
> такое объяснение было бы неверным.

**Условие свободной поверхности (traction-free):** при `r_norm = 1`
`σ_rr = 0` и `τ_rz = 0`. Сами данные FEM удовлетворяют ему с точностью
`|σ_rr| = 3.8` МПа, `|τ_rz| = 0.5` МПа — это и есть базовая линия, рядом с
которой только и осмысленно печатать нарушение ГУ у моделей.

### 2.6 Сравниваемые модели (шесть)

| Тег | Что это |
|---|---|
| MLP (grid) | обычный MLP, ручной грид-поиск 24 точки |
| MLP (Optuna) | тот же MLP, гиперпараметры через Optuna (TPE + MedianPruner) |
| PINN (PyTorch) | strong-form PINN, чистый torch + autograd |
| PINN (DeepXDE) | та же физика через DeepXDE |
| PINN (JAX/Flax) | та же физика на JAX/Flax |
| VPINN | вариационная (слабая) форма, синусоидальные тест-функции, квадратура Гаусса–Лежандра |

Общий шаблон: общий backbone + Fourier-эмбеддинг по r + одна линейная голова
на 4 выхода; OutputScaler (z-score по компонентам).

VPINN сравнивается как **отдельное семейство** (слабая форма), а не как
«ещё один бэкенд»: у него своя квадратура и свои λ.

### 2.7 Что заявлено как результат в отклонённой версии

- лучший hold-out macro-RMSE 11.51 МПа у PINN (JAX/Flax), на 1.71 МПа (13 %)
  лучше лучшего MLP;
- Friedman–Nemenyi: две группы, верхняя — три physics-informed конфигурации;
- «выбор бэкенда важен»: PyTorch и JAX/Flax лучше DeepXDE на 0.4–0.8 МПа;
- физаудит: нарушение ГУ у PINN 0.6–1.2 МПа против 12–20 МПа у MLP.

> **[изменено v2]** Последний пункт — самый ценный результат работы, но в
> нынешнем виде он не цитируем: ГУ налагалось при `r_norm = 1.5` (вне
> материала), а измерялось при `r_norm = 1` (E-01). Числа надо получить заново
> после перезапуска с `r_surface = 1.0`, и печатать их рядом с базовой линией

## 3. Что сказали рецензенты (дословно, англ.)

### Reviewer #1

> The manuscript addresses a relevant topic, and I appreciate the idea of comparing
> different data-driven and physics-informed ML approaches under a common framework.
> However, the current study does not provide a sufficiently basis for the rather
> general conclusions drawn.
>
> The main concern is the FEM model used to generate all training and validation data.
> The model is not experimentally validated, which is particularly critical because the
> entire ML comparison relies on these numerical results. In addition, it remains unclear
> whether the actual wire-drawing process, including the resulting residual stress state,
> can be represented with sufficient accuracy by the chosen axisymmetric Abaqus simulation.
> Without a proper validation of the FEM model, the study essentially evaluates how well
> different surrogate models reproduce one specific numerical model rather than the
> physical process itself.
>
> In addition, the comparison between the ML approaches is not fully controlled. Different
> implementations use partly different optimization strategies, making it difficult to
> attribute performance differences specifically to the selected PINN architecture or
> backend. The physics-informed formulation also requires further clarification,
> particularly regarding the use of axial derivatives although z is not included in the
> network input.
>
> Finally, the hold-out cases are generated from the same FEM model and parameter space.
> Thus, they demonstrate interpolation within this particular case, but not transferability
> or generalization beyond it.
>
> Overall, I find the underlying idea interesting, but in its present form the work is
> closer to a detailed case study than to a generally valid comparative assessment of
> physics-informed ML approaches. Addressing the central limitations would require
> substantial additional validation and methodological work rather than a normal revision.

### Reviewer #2

> The paper compares six surrogates for residual stress after wire drawing, but I could
> not identify a new method in it. The dataset, input parameterization and Optuna-tuned
> MLP baseline follow the authors' own refs [17] and [18]. What is added is a standard
> PDE penalty term and a comparison of three implementations of the same strong-form PINN
> in PyTorch, DeepXDE and JAX/Flax. A difference in autodiff backend is a software choice,
> not a modelling contribution, and the three implementations differ by 0.4 to 0.8 MPa in
> macro-RMSE on a single training run per model, with no seed repetition, so even that
> difference is not established.

### 4.1 Как переопределить вклад

R1-a непреодолим: эксперимента нет и не будет. Сейчас статья заявляет «общая
сравнительная оценка PINN-подходов» — рецензент справедливо отвечает, что это
case study. Защитимая рамка:

> «На одном контролируемом наборе FEM-данных показано, что физически-информированная
> регуляризация даёт **переносимость за пределы диапазона обучения** и **устойчивость
> к дефектам источника данных**, чего не даёт чисто датадривен-подход при равном
> протоколе обучения.»

Это утверждение проверяемо имеющимися данными (пункты 1, 5, 6) и не требует
экспериментальной валидации FEM: речь о свойствах суррогата относительно
источника, а не о точности воспроизведения физического процесса.

**[изменено v2] Что усиливает эту рамку.** Данные оказались дефектнее, чем
считалось: 13.2 % наборов — один расчёт под несколькими метками трения, один
уровень фактора порождён опечаткой в имени задания, целый уровень `Q = 0.25`
вырожден. Это не только проблема — это **материал для основного тезиса**:
источник данных промышленного расчёта содержит систематические дефекты, и
устойчивость суррогата к ним есть практически значимое свойство. Пункт 6
(порча меток) из вспомогательного эксперимента становится центральным.

**Что писать нельзя.** Что дефекты обнаружены «в ходе валидации пайплайна» —
часть из них воспроизведена и в отклонённой версии. Честная формулировка: при
подготовке пересабмита проведён аудит источника, его результаты приведены
полностью, часть чисел прошлой версии в результате пересчитана.

### 6.3 Обязательные конвенции (нарушение = невалидный результат)

1. **Физлоссы только в нормированных координатах.** В физических — mode collapse.
2. **Group-aware split обязателен**: все 20 r-точек одного набора в одном фолде.
   Никакого row-level random split.
3. **`PLANE_ORDER` применять и к предсказаниям, и к эталону** — и сначала
   проверить его на самом `.pkl` (§5.1).
4. **Скейлеры фитятся только на train** (`OutputScaler().fit(y_tr)`,
   `X_tr.mean(0)`). При экстраполяции нормированные тестовые входы выйдут за
   [−1, 1]: **это нормально, не клипать.**
5. **Seed фиксировать всегда**, и не один — см. пункт 3.
6. **Фильтры до сплита**, не после.
7. `os.environ["DDE_BACKEND"] = "pytorch"` **до** `import deepxde`.
8. В DataLoader не использовать `torch.Generator(device=...)` вместе с
   `dde.set_default_device` — ручной `torch.randperm` + `index_select`.
9. Сен-Венан (совместность) — только к полным деформациям (LE), не к
   пластическим; `λ_compat` поднимать до 0.1–1.0, не 1e-4. (Для будущей работы
   по деформациям.)
10. **[новое v2] Свободная поверхность при `r_norm = 1.0`**, не 1.5. ГУ
    налагать и измерять в одной точке (`physics_check.R_FREE_SURFACE`).
11. **[новое v2] `R₂` не называть осевым равновесием** ни в коде, ни в статье.
12. **[новое v2] Ранговые тесты — по сидам и внутри сплита.** Объединять
    сплиты в общий пул нельзя (`stats.pool_guard` падает).
13. **[новое v2] Никогда не опознавать содержимое `.pkl` по одной проверке,
    которую проходит несколько раскладок.** Опознание — только сопоставлением
    с источником по всем кандидатам (`verify_pkl.py`).
14. **[новое v2] Сортировка в препроцессинге — устойчивая.** Иначе пайплайн не
    воспроизводит сам себя (E-21).

### 6.4 Интерпретация метрик

- Низкий R² на низковариативных наборах — **патология метрики**, а не ошибка
  модели; основная метрика — RMSE (МПа). Всегда проверять RMSE прежде чем
  делать вывод.
- Преимущество PINN искать **на хвосте распределения** (артефакты, low-signal),
  а не только в средней RMSE.
- Равновесные невязки ограничены снизу шумом FEM: их нельзя улучшить
  data-loss'ом. BC-loss даёт физприор независимо от качества данных — **это
  ключевой аргумент работы**, и именно поэтому его надо померить корректно
  (E-01).
- **[изменено v2]** Абсолютные величины невязок сильно зависят от способа
  агрегирования (среднее против медианы при особенности `1/r` у оси) и от того,
  в каких координатах считается производная. В статье указывать и то, и другое;
  числа из разных версий не сопоставлять между собой без пересчёта.
- Старый результат «MLP бьёт PINN, R² 0.97 против 0.85» **невалиден** (физика
  была фактически отключена слишком малым λ) — не цитировать.

### 7.0 Пересобранный датасет

`dataset.py` берёт из `.rpt` колонки `S.S11`, `S.S33`, `S.S22`, `S.S12` —
истинные `(σ_rr, σ_θθ, σ_zz, τ_rz)`, сворачивает узлы осевого окна в 20
радиальных бинов и нормирует радиус на радиус поверхности того же набора, так
что `r = 1` есть поверхность по построению. После фильтров — **1848 наборов**.

Проверки, которые печатаются перед каждым прогоном и которых прежние целевые
поля пройти не могли:

| величина | значение |
|---|---|
| `\|σ_rr\|` на поверхности | 3.56 МПа |
| `\|τ_rz\|` на поверхности | 0.33 МПа |
| `\|τ_rz\|` на оси | 0.21 МПа |
| `r` крайней точки | ровно 1 |

Первые две строки — traction-free, третья — осевая симметрия. Это же и базовая
линия для физаудита: точное условие `σ_rr = τ_rz = 0` есть приор, которому сам
источник удовлетворяет лишь с такой точностью.

### 7.0.1 Единый тренер

Один класс сети, один оптимизатор (AdamW), отсутствие планировщика, одинаковые
эпохи, батчи, ранняя остановка и сиды у всех семейств. Семейство меняет
**только** состав функции потерь:

| семейство | что добавлено к data-loss |
|---|---|
| `mlp` | ничего |
| `pinn` | `λ_bc·BC` + `λ_phys·` сильная невязка `R₁` (autograd по r) |
| `vpinn` | `λ_bc·BC` + `λ_phys·` слабая форма: проекция `R₁` на `sin(kπr)`, квадратура Гаусса–Лежандра, интегрирование по частям (производная сети не вычисляется вовсе) |

Осевое уравнение не используется: без `∂σ_zz/∂z` оно не является уравнением
равновесия (E-02). Сдвиговый член доступен отдельным `λ_shear` и называется
регуляризатором гладкости, а не равновесием.

ГУ налагается и измеряется при `r = 1` — в одной и той же точке (E-01).

Масштабы невязок нормированы физически (`σ_std / R`). Без этого `log1p(res²/scale)`
уводит физлосс на пять порядков ниже data-loss, и физика оказывается фактически
выключенной независимо от λ — та же ошибка, из-за которой в старом результате
«MLP бил PINN».

### 7.0.1а Что нашло состязательное ревью собственного кода

Прежде чем результаты пошли в отчёт, весь численный код был отдан на
состязательное ревью: пять независимых проходов по разным линзам (физика и
размерности, утечки и сплиты, честность сравнения семейств, метрики,
статистика), каждая находка — проверке отдельным агентом с запуском. Нашлось
четыре дефекта, каждый из которых обесценивал часть выводов. Их стоит знать не
ради истории, а потому что три из четырёх — ровно те классы ошибок, из-за
которых отклонили статью.

**1. Ложный заголовочный вывод «за диапазоном модель хуже предсказания
средним».** Отрицательный macro-R² создавался целиком компонентой τ_rz: её
локальный R² = −4.4 при доле 2 % в macro-RMSE, и знаменатель брался по тому же
срезу, где дисперсия τ_rz вдвое меньше. Проверка: предсказание константой даёт
60 МПа против 22 у моделей. С единым знаменателем R² = +0.39 за диапазоном
против +0.53 внутри, а по трём нормальным компонентам +0.91 против +0.97 —
плавная деградация, а не смена знака. `metrics()` теперь считает нормированные
величины дважды, локально и глобально, и отчёт печатает глобальные.

**2. Слабая форма была численно инертна.** Её физлосс давал 0.36 % от нормы
градиента data-члена против 37 % у сильной, то есть семейство `vpinn` было
фактически «`mlp` + штраф ГУ», а сравнение форм измеряло «физика включена
против выключенной». Сам вывод слабой формы верен (невязка 2.4e-13 на
аналитическом поле, точно удовлетворяющем равновесию) — дефект был в
нормировке: слабый член есть проекция того же остатка на осциллирующие
тест-функции, и она гасится примерно в 200 раз, а `log1p(x²)` возводит гашение
в квадрат.

Это **тот же по классу дефект**, из-за которого в отклонённой версии физика
была отключена слишком малым λ. Поэтому чинилось не константой, а причиной:
введена калибровка веса физики по норме градиента, и `lambda_physics` теперь
означает «физический градиент составляет λ от data-градиента» одинаково у всех
семейств. Измеренные множители: 0.162 у сильной формы и 4.87 у слабой —
расхождение было 30-кратным.

**3. Гейт значимости объявлял разницу установленной при p = 0.12**, а при одном
сиде — всегда, включая Δ = 0 (потому что σ = 0). Заменено на парный тест по
сидам с порогом не менее трёх сидов; критерий |Δ| ≥ σ оставлен отдельной
величиной как размер эффекта.

**4. `cliques()` строил CD-окрестности вместо максимальных клик** и печатал
ровно ту формулировку, которую `ERRATA` E-15 помечает как ошибку аннотации
отклонённой версии: при рангах 1.2 / 2.0 / 2.8 и CD = 1.48 выдавал одну группу
из трёх, скрывая различимую крайнюю пару. Отчёт теперь печатает и список
различимых пар.

Плюс: в `trainer2d` осевая невязка нормировалась радиальным масштабом вместо
осевого (L/R = 3.7), из-за чего абляция «полная против редуцированной формы»
ничего бы не показала. `L_char` вычислялся и нигде не использовался — прямая
опечатка, найденная по `grep`.

**Вывод для того, кто продолжит.** Ни один из четырёх дефектов не ловится
тестами на инварианты — все они дают правдоподобные числа. Ловятся они только
двумя приёмами: измерять влияние члена лосса (норма градиента), а не доверять
его номинальному весу, и всегда печатать нулевую модель рядом с метрикой.
Оба приёма встроены в код.

### 7.0.2 Вопрос про бэкенды закрыт аналитически

Вопрос распадается на два, и в отклонённой версии они были смешаны.

**Считают ли движки одно и то же?** `check_gradient_agreement()` строит одну и
ту же сеть с побитово одинаковыми весами в torch и в JAX и сравнивает
`∂σ_rr/∂r`:

```
max|Δ| прямого прохода   1.0e-15
max|Δ| ∂σ_rr/∂r          8.7e-15   (относительная 9.8e-16)
```

Вместе с тем, что DeepXDE в репозитории работает на PyTorch (E-19), это значит:
разницу 0.4–0.8 МПа между «бэкендами» **нечем объяснить со стороны
автодифференцирования**.

**Различаются ли две независимые реализации сильнее, чем прогоны одной?** Это
содержательный вопрос, и стадия `backend` ставит его честно: обе реализации
делят архитектуру, протокол, данные, разбиение и гиперпараметры, но начальные
веса и порядок батчей берут из своих генераторов, и каждая гоняется на пяти
сидах. Требовать побитово одинаковой инициализации здесь не нужно — это свело бы
эксперимент к проверке детерминизма вместо вопроса «отличима ли смена движка от
разброса перезапусков».

### 7.1 Сплиты

Вместо случайного 15 % hold-out из обучения выносится **целая грань**
факторного пространства.

| Сплит | Held-out | вид |
|---|---|---|
| `extrap:alpha_max` | α = 20° | экстраполяция |
| `interp:alpha_mid` | α = 12° | **контроль**, внутри диапазона |
| `matched:alpha_max` | случайные наборы того же размера | **контроль** |
| `extrap:Q_high` | Q = 0.20 | экстраполяция |
| `interp:Q_mid` | Q = 0.10 | контроль |
| `extrap:k_max` | k = 1.0 | экстраполяция |
| `extrap:v_max` | v = 250 м/мин | экстраполяция |
| `extrap_joint:corner` | α = 20° и Q ≥ 0.15 | дыра в совместном пространстве |
| `random` | исходный сплит статьи (15 %) | интерполяция |

Объёмы на фильтрованной сырой сетке (1848 наборов) — как порядок величины;
на `.pkl` пересчитать через `summarize_suite`:

```
extrap:alpha_max      1461 / 387      экстраполирует по alpha
matched:alpha_max     1461 / 387      —
interp:alpha_mid      1469 / 379      —
extrap:Q_high         1542 / 306      экстраполирует по Q
extrap:k_max          1544 / 304      экстраполирует по k
extrap:v_max          1344 / 504      экстраполирует по v
extrap_joint:corner   1728 / 120      дыра в совместном пространстве
random                1571 / 277      —
```

**Основная пара для статьи: `alpha_max` против `alpha_mid`** — объёмы близки,
но первый лежит вне диапазона обучения, второй внутри. Самый чистый контраст
«экстраполяция / интерполяция».

**[изменено v2] Про `corner`.** Прежний handover числил его экстраполяционным.
Формально это не так: `train` по-прежнему содержит и α = 20°, и Q = 0.2 — просто
не вместе. По каждой оси в отдельности test внутри диапазона train. Это дыра в
совместном пространстве, и `coverage_report` честно ставит «нет» по всем осям.
Заявлять по нему «выход за диапазон обучения» нельзя; заявлять «непокрытая
область совместного пространства» — можно, это отдельное и тоже полезное
утверждение. `make_region_split` падает, если сплит объявлен `extrap`, но по
факту не выходит за диапазон ни по одной оси.

**Защита от подделки результата.** `coverage_report()` печатает по каждой оси
диапазоны train и test и колонку «вне диапазона?». Заявлять обобщение можно
**только** по осям, где стоит «ДА». Пересечение наборов train/test — ноль
(проверяется `assert`).

μ как ось экстраполяции **не используется** (§5.4).
