# Письмо руководителю: что нужно проверить в расчётах Abaqus и зачем

Дмитрий, добрый день.

По итогам разбора данных для новой версии статьи есть три вопроса, которые
нельзя закрыть из отчётов `.rpt`. Все они решаются на рабочей станции, где
лежат `.odb`/`.inp` и стоит Abaqus. Ниже — что именно проверить, зачем и что
прислать обратно. Скрипты и списки в папке `publication/reexport/` репозитория
(ветка `claude/errors-new-playbook-9grlm7`), они же приложены к письму.

## 1. Выгрузить усилие волочения для 30 режимов (главное)

**Зачем.** Рецензенты просили сравнить МКЭ с аналитикой (Зибель, Авитцур).
Для этого нужно напряжение волочения σ_d = F/A. В имеющихся отчётах
выгружен только последний кадр, когда проволока уже вышла из волоки и
сечение разгружено, поэтому усилие из них извлечь нельзя. Сейчас σ_d удалось
получить только из 158 расчётов, которые оборвались, пока проволока была в
волоке (там F/A видно по σ_zz в протянутой части). Сходимость с формулами
хорошая (MAPE 8.8 % по Зибелю и 5.7 % по Авитцуру), но опираться в статье на
«бракованные» расчёты нельзя. Нужна реакция на опорной точке волоки `RF` по
всем кадрам хотя бы для 30 режимов из самого датасета.

**Заодно выгружаются** `PEEQ` (фактор избыточной деформации, сейчас есть
только нижняя оценка по `LE`), `CPRESS`/`CSHEAR` (контактные напряжения для
члена трения) и `TEMP`/`NT11`. Последнее нужно, чтобы документально
подтвердить, что расчёт не термомеханический: в полях это уже видно (нет
чувствительности к скорости, объёмная деформация чисто упругая), но
рецензент спрашивал про температуру прямо.

**Как.** На рабочей станции с дисками E:, H:, V:

```
python check_odb_alive.py reexport_list.csv
abaqus python reexport_fields.py reexport_list.csv out_dir
```

Первая команда за минуту показывает, какие из 30 `.odb` на месте (Abaqus не
нужен, обычный Python). Вторая делает выгрузку; сначала стоит прогнать на
2–3 файлах и посмотреть `out_dir/missing.txt`.

**Что прислать.** Папку `out_dir` целиком и `alive.csv`.

## 2. Проверить, варьировалось ли трение (E-23)

**Что обнаружено.** В 159 семействах расчётов (одинаковые Q, k, α, v, три
уровня μ) числовой блок отчёта побитово совпадает при всех трёх значениях
трения, вплоть до номера инкремента (например, 13 410 482 у трёх якобы
разных расчётов семейства `1020_2a_40_rd_1000_cal_100_v_10`). Пути к `.odb`
при этом разные. Так быть не может, если трение действительно отличалось.
Затронуто 477 расчётов из 2443, почти все при v = 10 и 20 м/мин.

**Зачем.** В обучение эти наборы не попадают (сняты как дубликаты), но в
статье заявлен факторный план 7×6×5×3×5, а по μ он покрыт хуже. Надо либо
честно оговорить, либо досчитать.

**Как.** Взять из `e23_friction_not_varied.csv` любое семейство, открыть три
его `.inp` и сравнить блок `*FRICTION`. Если там одно и то же значение, то
ошибка была на входе, и досчёт требует новых `.inp`. Если значения разные,
то `.odb` скопированы под три имени, и нужно найти, где лежат настоящие.

**Что прислать.** Ответ, какой из двух случаев, и по возможности три `.inp`
одного семейства.

## 3. Незавершённые расчёты (E-24)

**Что обнаружено.** 158 расчётов оборвались до того, как проволока прошла
волоку целиком: на ней остался участок исходного радиуса 18 мм, а опорная
точка волоки стоит внутри размаха проволоки. При Q = 0.25 таких 17 %, на
остальных уровнях 4–6 %. Из датасета они сняты (1848 → 1756), и это дало
треть точности всех моделей: в окне 25–75 % у них лежит контактное давление
волоки до −571 МПа вместо остаточных напряжений.

**Зачем.** Для статьи достаточно снять их и оговорить. Пересчитывать имеет
смысл только уровень Q = 0.25: он сейчас исключён целиком, и с ним ось Q
была бы длиннее. Это на ваше усмотрение.

**Как.** Список в `e24_unfinished_runs.csv` с путями к `.odb`. Проверить по
`.sta`/`.msg` двух-трёх заданий, почему оборвался расчёт (лимит времени,
искажение сетки, лицензия).

**Что прислать.** Причину обрыва по 2–3 заданиям; если решите досчитывать
Q = 0.25, новые `.rpt` в том же формате, что прежние.

## Что приложено

| файл | что это |
|---|---|
| `check_odb_alive.py` | проверка, какие `.odb` существуют; обычный Python |
| `reexport_fields.py` | выгрузка `RF`, `PEEQ`, `CPRESS`, `CSHEAR`, `S`, `LE`, `COORD`, `TEMP` по кадрам; запускать через `abaqus python` |
| `reexport_list.csv` | 30 отобранных режимов с путями к `.odb` (все уровни Q, k, v, μ; α = 4, 8, 20°) |
| `all_odb_paths.csv` | пути ко всем 2443 `.odb`, если захотите проверить всё |
| `e23_friction_not_varied.csv` | 159 семейств, где отчёты при трёх μ идентичны: семейство, инкремент, пути к трём `.odb` |
| `e24_unfinished_runs.csv` | 158 незавершённых расчётов: параметры, максимальный радиус, путь к `.odb` |
| `README.md` | порядок действий и описание выгружаемых полей |
| `../VALIDATION.md` | что уже проверено по имеющимся отчётам: равновесие, свободная поверхность, материальная карта, Зибель/Авитцур |
